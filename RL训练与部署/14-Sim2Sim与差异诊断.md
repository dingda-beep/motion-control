# 14 Sim2Sim 与差异诊断

## 14.0 第二仿真器消费的是冻结发布包

```text
# 输入必须冻结；测试时若修改 scale、PD 或模型，就无法判断差异来自哪里。
sim2sim_report = run_in_second_simulator(
    policy_onnx,                       # 与训练候选完全相同的 Actor
    deploy_contract,                   # 同一观测、动作、周期和关节映射
    second_robot_model,                # 在另一物理实现中重建的同一机器人
    fixed_command_and_disturbance_suite # 固定命令、扰动、边界与长时测试集
)
# 输出是跨引擎的指标与逐层差异报告，不会产生一个“修好后的新策略”。
```

输出是差异报告，不是一个新策略。若测试过程中悄悄改变动作比例或网络参数，输入已经不再冻结，也就失去了定位差异的意义。

## 14.1 为什么训练仿真通过后还要换 MuJoCo

如果训练和测试都使用同一物理引擎、同一机器人资源和同一任务代码，一些错误会被共同保留：

- 接触参数只适合该求解器；
- 执行器模型的实现细节被策略利用；
- 训练与 play 共享同一个错误观测；
- 模型资源中的惯量、碰撞体或关节设置有特殊解释。

把冻结策略放进另一个物理实现，可以打破一部分共同假设。这不是为了证明 MuJoCo 就是真实世界，而是增加一个独立证据来源。

## 14.2 Sim2Sim 前先冻结接口

不要一边换仿真器一边改奖励、观测和策略。输入应固定为：

```text
同一个 policy.onnx
同一份部署契约
同一组命令脚本
同一默认姿态和关节映射
尽量对应的机器人参数
```

Sim2Sim 失败时才能归因于接口或环境差异，而不是模型已经变了。

## 14.3 按层排查，不要先怪“动力学差异”

### 第一层：纯推理

固定 480 维输入，检查两个运行时的 29 维输出。不同则是模型导出、normalizer、数据类型或运行时问题。

### 第二层：观测构造

冻结原始机器人状态，逐项比较观测。不同则看坐标系、单位、顺序、缩放、历史缓存和默认姿态。

### 第三层：动作处理

固定 actor 输出，比较最终关节目标和 SDK/仿真关节顺序。不同则看 scale、offset、clip 和 joint map。

### 第四层：开环执行器响应

对两个仿真器施加相同的小幅关节目标脚本，比较位置、速度、力矩响应。不同则看 PD、力矩限制、执行器和积分周期。

### 第五层：接触与闭环

前四层一致后，再比较站立、落脚、足滑和行走。此时差异才更可能来自接触、惯量、柔性和求解器。

## 14.4 常见现象怎样读

| 现象 | 优先检查 |
|---|---|
| 一进入策略全身猛跳 | 默认姿态、动作比例、关节顺序、PD 增益 |
| 能站但无法跟命令 | 命令顺序/范围、坐标系、观测缩放 |
| 步态节奏快一倍 | 策略周期、decimation、历史时间跨度 |
| 原引擎稳定，MuJoCo 足部滑 | 摩擦、接触几何、足底材料、力矩响应 |
| 几秒后逐渐发散 | 状态估计漂移、历史更新、延迟、执行器积累误差 |
| 只向某一侧倒 | 左右关节映射、符号、默认姿态、质量不对称 |

## 14.5 不要为了通过 Sim2Sim 在部署端偷偷补丁

例如发现 MuJoCo 中动作过大，直接在部署端把 scale 从 `0.25` 改成 `0.15`，确实可能暂时稳定。但这已经改变训练策略的动作语义。

正确流程是：

1. 把差异形成可复现实验；
2. 判断是配置错误、模型差异还是策略鲁棒性不足；
3. 若需要改动作接口，回到训练与评估共同修改；
4. 生成新候选版本，重新做等价性和评估。

## 14.6 Sim2Sim 的通过标准

不要求两个引擎轨迹逐点相同。混沌接触系统经过一段时间自然会分叉。应比较任务与安全统计：

- 速度跟踪误差分布；
- 姿态与高度范围；
- 关节/动作/力矩极值；
- 足滑和非期望接触；
- 扰动恢复成功率；
- 长时存活与失败类型。

要求的是在批准包络中保留能力和安全裕量，而不是像素级复刻训练视频。

当前 Unitree RL Lab 的官方部署流程明确把 MuJoCo Sim2Sim 放在 Sim2Real 之前，具体启动方式应核对[官方仓库](https://github.com/unitreerobotics/unitree_rl_lab)与你安装的版本。

# 15 真机控制程序与安全状态机

## 15.0 真机每一周期的准确调用关系

```text
# 1. 从真实硬件读当前反馈，并保留采样时间；q、dq 不是网络输出。
q, dq, imu, state_time = sdk.read_state()

# 2. 从遥控器/导航器读上层目标；命令也必须带更新时间以检测失联。
vx_cmd, vy_cmd, vyaw_cmd, command_time = command_source.read()

# 3. 先检查反馈和命令是否仍可用；拒绝时直接转入批准的回退状态。
safe_or_reason = safety_gate(state, command, timing)

# 4. 只有通过安全检查，才把反馈、命令和控制器记忆拼成 Actor 观测。
obs = observation_builder(state, command, last_action, history)

# 5. ONNX Actor 只做“观测 → 29 维原始动作”的前向计算。
raw_action = onnx_actor(obs)

# 6. 加默认姿态、缩放、限幅并重排关节，得到 SDK 顺序的 q_des。
q_des = action_processor(raw_action)

# 7. 发送完整位置式 PD 电机包；低层用最新 q、dq 形成实际力矩。
sdk.send(q_des, dq_des=0, kp, kd, tau_ff=0)
```

任何一步失败都不应继续假装后面的输入有效。安全门输出拒绝时，控制权交给经过验证的回退状态，而不是继续调用 actor。

## 15.1 真机程序不只是 `session.run(obs)`

一个最小但完整的结构是：

```text
状态接收线程 ──→ 最新状态快照 + 时间戳
                         ↓
命令接收线程 ──→ 命令整形 ──→ 控制线程
                                  ├─ 安全检查
                                  ├─ 观测与历史
                                  ├─ ONNX 推理
                                  ├─ 动作处理
                                  └─ 低层命令发布
                                          ↓
                                 状态机 / 故障回退
```

日志线程应异步记录关键量，避免磁盘写入阻塞控制周期。

## 15.2 为什么需要状态机

行走策略只熟悉特定入口状态，不能承担整个上电生命周期。典型状态概念包括：

```text
Passive       不输出主动运动目标
Prepare       检查通信、传感器、模型和配置
StandUp       用受控轨迹进入默认站姿
Ready         确认姿态、关节和状态新鲜度
RL            策略接管
SafeStop      按批准方式退出主动动作
Fault         故障锁存，等待人工处理
```

状态名可以不同，关键是每次切换有明确守卫条件。例如从 `Ready` 到 `RL` 不能只由一个按钮触发，还应要求状态新鲜、姿态正常、关节在接管范围、模型契约匹配、急停可用。

## 15.3 看门狗在看什么

每个控制周期至少检查：

- 机器人状态是否在允许时间内更新；
- 命令是否超时；
- 观测和动作是否全为有限数，拒绝 NaN/Inf；
- IMU 四元数是否有效，姿态是否超出批准包络；
- 关节位置、速度、目标变化和力矩反馈是否异常；
- 控制线程是否连续错过 deadline；
- 模型、契约和机器人型号是否匹配；
- SDK 是否报告故障、失联或模式冲突。

发现异常后必须走预先审核的状态转换。不要在异常分支里继续调用策略碰碰运气。

## 15.4 “保持最后动作”为什么危险

状态失联后复用最后一个关节目标，看起来比输出随机数合理。但若机器人正在倒，最后动作是根据旧姿态计算的；持续保持可能加速错误。

正确回退依赖机器人硬件和现场条件，可能是进入阻尼模式、受控缓停、切回厂家安全控制或断开主动输出。教程不能替具体机器人指定统一动作，但可以规定：

> 回退行为必须被独立设计、在仿真和受控现场验证，并且不依赖失联后的策略继续正确工作。

## 15.5 实时循环的原则

控制线程中应避免：

- 动态下载或查找模型；
- 大量内存分配；
- 同步写磁盘；
- 阻塞等待网络；
- 临时解析大配置；
- 无上限重试。

初始化阶段完成模型加载、schema 校验、缓冲区分配和预热。运行阶段记录周期耗时，超时进入计数和保护逻辑。

“在普通循环中平均能跑 50 Hz”和“具备实时保障”不是同一句话。后者还涉及操作系统调度、线程优先级、CPU 亲和性、内存锁定、总线和最坏时延，需要结合目标硬件专门验证。

## 15.6 观测使用的不是上帝视角真值

真机链路是：

```text
x_real
  → y = h_real(x_real) + noise
  → estimator(y, u, f_model)
  → x_hat
  → observation builder
  → actor
```

- `x_real`：真实状态，无法完整直接读取；
- `y`：IMU、编码器等传感器测量；
- `h_real`：现实测量过程；
- `noise`：噪声、偏置、量化等误差；
- `u`：系统最近实际执行或被要求执行的控制输入，估计器可用它预测机器人为何会这样运动；
- `f_model`：估计器内部的运动/动力学预测模型；
- `x_hat`：估计器对当前状态的判断。

actor 实际看见的是由 `x_hat` 和其他可用信号构造的观测，不是仿真器方便提供的 `x_real`。训练观测必须围绕这条部署可实现链路设计。

## 15.7 当前官方示例给了什么启示

当前 Unitree RL Lab 的 G1 部署代码会加载 `deploy.yaml` 和 `policy.onnx`，把处理后的动作按 `joint_ids_map` 写入低层电机命令，并注册不良姿态退出检查。这说明模型推理始终嵌在配置解析、关节映射和状态机里。

它是一份有价值的参考实现，但不自动构成你现场的完整安全认证。官方 README 还提示真机直控前必须处理机载控制程序冲突；这类模式切换属于高风险操作，应严格依照对应机器人版本的官方文档和现场负责人流程执行。

SDK 与部署入口请从 [Unitree RL Lab](https://github.com/unitreerobotics/unitree_rl_lab) 和 [Unitree SDK2](https://github.com/unitreerobotics/unitree_sdk2) 的当前官方版本核对。

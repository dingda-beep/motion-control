# 03 机器人模型与关节映射

## 3.0 仿真器把机器人模型当成什么接口

可以先把物理引擎理解成：

```text
next_state, contacts = physics_step(
    current_state,
    motor_command,
    robot_parameters,
    world_parameters,
    dt
)
```

机器人描述、执行器参数和地面参数进入这个函数，输出下一时刻状态与接触。RL 不会绕开它；策略看到的每一条训练经验，都是这个函数预测出的后果。

## 3.1 URDF/USD 给出了什么，没有给出什么

机器人描述文件通常提供：

- 连杆如何连接；
- 关节轴、限位和初始关系；
- 碰撞与视觉几何；
- 质量、质心和惯量；
- 某些执行器或传动信息。

但“有一份 URDF”不等于仿真已经等同真机。电机电流环、减速器摩擦、背隙、结构柔性、线缆、鞋底材料、通信延迟、传感器滤波和接触求解参数，往往需要额外配置、辨识或随机化。

模型不是现实的身份证复印件，而是仿真器用于预测下一时刻的近似规则集合。

## 3.2 同一组关节可能有两种顺序

假设训练端动作前六维按下面排列：

```text
[左髋俯仰, 右髋俯仰, 腰偏航, 左髋横滚, 右髋横滚, 腰横滚, ...]
```

而 SDK 的电机数组前六项是：

```text
[左髋俯仰, 左髋横滚, 左髋偏航, 左膝, 左踝俯仰, 左踝横滚, ...]
```

两边都是 29 维，程序不会因为长度不对而报错；它只会把“右髋俯仰目标”悄悄发给“左踝横滚”。这是最危险的一类错误：**形状正确，语义错误。**

当前官方 G1 示例导出的映射是：

```text
policy index → SDK motor index
[0, 6, 12, 1, 7, 13, 2, 8, 14, 3, 9, 15, 22, 4, 10,
 16, 23, 5, 11, 17, 24, 18, 25, 19, 26, 20, 27, 21, 28]
```

例如策略第 1 维映射到 SDK 第 6 号电机。这个数组应由当前机器人与训练模型导出并做双射检查，不能凭记忆手抄成“永久真理”。

## 3.3 映射必须是双射

对 29 个受控关节，合法映射应满足：

1. 长度正好为 29；
2. 每个目标索引都在 `0..28`；
3. 没有重复；
4. 没有遗漏；
5. 名称、方向、零点和单位逐关节核对。

数学上这叫双射：每个策略关节只对应一个电机，每个受控电机也只被一个策略关节占用。

## 3.4 默认姿态是动作语义的一部分

本案例不是让网络直接输出绝对关节角。目标是：

\[
q_i^{target}=q_i^{default}+0.25a_i
\]

其中：

- \(a_i\)：网络第 \(i\) 个输出，通常处于归一化范围附近；
- `0.25`：动作比例，单位 rad；
- \(q_i^{default}\)：训练配置中的默认关节角；
- \(q_i^{target}\)：交给低层 PD 的目标角。

如果训练端默认膝角是 `0.3 rad`，部署端却用 `0`，那么当策略输出零时，两个世界里的机器人姿态已经不同。默认姿态不能只存在于训练源码里，它必须进入部署契约。

## 3.5 参数的四个来源

工程中经常同时存在：

```text
机械设计/厂家标称值
→ URDF/USD 中的模型参数
→ 仿真任务为训练稳定性设置的执行器参数
→ 真机低层控制实际采用的参数
```

它们可能不同。发现不同时，不应擅自挑一个看起来顺眼的数字，而要记录：参数表示什么、作用在哪一层、为何不同、导出时取自哪里。

例如“最大力矩”可能分别表示电机峰值、持续允许值、仿真软限制和控制器主动限幅。名字相近并不保证物理含义相同。

## 3.6 上电前的单关节核对

在电机不使能或机器人可靠支撑的条件下，对每个关节完成：

1. 手动移动关节，确认 SDK 读数变化的索引；
2. 确认正方向与训练模型一致；
3. 确认零位与默认姿态定义；
4. 小幅目标测试，不加载策略；
5. 记录位置、速度、力矩反馈和饱和标志；
6. 自动生成映射报告并由第二人复核。

这一步很慢，却比让全身策略替你发现映射错误便宜得多。

## 怎么读这一章

这一章不再逐个模块背定义，而是追踪同一个任务：

> 机器人收到“去厨房”的目标，开始行走；右脚落地后地面突然打滑，系统怎样发现、修正、降级并留下证据？

第一遍只读第 1～4 节，跟住这条因果链：

```text
人的目标
→ 路径
→ 落脚与身体参考
→ 当前关节命令
→ 真实机器人运动
→ 传感器测量
→ 状态估计
→ 下一轮修正
```

第二遍再读多频率、状态机、安全和日志。第 9 节的端到端架构属于方法比较，不影响理解主线。

## 1. 为什么“去厨房”不能直接发给电机

人说：

```text
去厨房。
```

电机却只理解类似下面的东西：

```text
左膝期望位置是多少
右踝期望速度是多少
每个关节此刻请求多大力矩
```

“去厨房”和“右膝输出 `8 N·m`”之间相差太远，必须经过多次翻译：

```text
去厨房
→ 从当前位置绕过桌子进入走廊
→ 未来几步分别踩在哪里
→ 质心、躯干和摆动脚怎样运动
→ 当前这一毫秒各关节发什么命令
```

不同翻译面对的问题不同：

- 地图层关心墙和桌子，不应该直接处理电机电流；
- 步态层关心未来几步，不可能等待每个电流环算完再思考路径；
- 电机层必须在极短时间内响应，没时间重新理解“厨房”是什么。

分层不是为了制造名词，而是因为同一个问题同时存在不同空间尺度、时间尺度和信息粒度。

先看任务成功时的完整链条：

```text
人的任务：去厨房
↓
导航：选择经过走廊的路径
↓
运动规划：安排左右脚落点、接触时序和身体参考
↓
控制器：根据当前状态估计，把参考变成关节命令
↓
驱动器：尝试让电机实现命令
↓
真实机器人与地面：产生真实运动
↓
传感器：测到运动结果的一部分
↓
状态估计器：判断机器人现在在哪里、怎样运动、脚是否踩稳
↓
导航、规划和控制器根据新判断继续工作
```

最后一条回边说明：这不是一次从上到下的流水线，而是持续闭环。

## 2. 同一个任务经过哪些模块

### 2.1 Navigation：先决定“从哪里走”

Navigation 是导航。

机器人知道自己在客厅、厨房在走廊另一端，地图中间还有一张桌子。导航模块输出的不是关节角，而是一条较粗的路径：

```text
当前位置
→ 从桌子右侧绕过
→ 进入走廊
→ 到达厨房门口
```

它主要使用：

- 地图和障碍物；
- 机器人在地图中的位置估计；
- 目的地；
- 可通行区域和身体大致尺寸。

它主要输出：

```text
未来应该经过的空间路径或局部行进方向
```

导航能判断“桌子左侧太窄”，却通常不会计算右踝关节这一毫秒需要多少力矩。

### 2.2 Planning：再决定“身体和脚怎样走”

Planning 是运动规划。

导航只说“沿走廊向前”，运动规划还要把它变成身体能够尝试跟踪的参考：

```text
先由左脚支撑
→ 右脚抬起
→ 右脚落在前方 0.25 m
→ 短暂双脚支撑
→ 再抬左脚
```

规划器可能输出：

- 哪只脚在什么时候接地；
- 摆动脚的抬脚、前摆和落脚轨迹；
- 质心和躯干参考轨迹；
- 手臂是否需要配合摆动；
- 未来接触序列。

这些是 **参考**，不是现实保证。

规划器写下“右脚将在 `12.37 s` 落地”，只表示后续模块应该尝试实现这件事。它不能让现实地面承诺右脚一定按时、无滑动地接触。

### 2.3 Estimator：判断机器人“现在究竟怎样”

Estimator 是状态估计器。

控制器不能读取上帝视角的真实状态 `x_real`。它只能收到传感器测量 `y`，例如：

```text
IMU（Inertial Measurement Unit，惯性测量单元）的角速度和加速度
关节编码器读数
足底压力或力传感器读数
相机和定位结果
```

状态估计器结合测量、旧估计、旧命令和内部模型，形成：

```text
x_hat = 对当前状态最合理的判断
```

对这次“去厨房”任务，它可能给出：

```text
身体位置和姿态
身体线速度和角速度
所有关节位置和速度
左脚是否可靠支撑
右脚是否已经落地
某只脚是否疑似打滑
```

规划器和控制器实际使用的是 `x_hat`，不是完整的 `x_real`。

### 2.4 Controller：把参考变成当前命令

Controller 是控制器。

它同时拿到：

```text
规划器给出的参考
+ 状态估计器给出的 x_hat
+ 机器人模型和限制
```

然后回答：

> 为了让真实运动继续接近参考，当前这一周期应该发出什么关节命令？

输出可能是：

- 关节位置目标；
- 关节速度目标；
- 关节力矩命令；
- 位置、速度目标与 PD（Proportional-Derivative，比例—微分）增益的组合。

WBC（Whole-Body Control，全身控制）、MPC（Model Predictive Control，模型预测控制）或学习策略，都可能出现在这条决策链的某一层。但它们不是整套机器人系统本身。

### 2.5 Driver：把软件命令交给真实执行器

Driver 是驱动器接口或底层执行器控制。

控制程序给出的命令记为 `u`。驱动器、电机、减速器和传动系统最终在现实中实现的作用记为 `u_real`：

```text
控制命令 u
→ 通信与驱动器
→ 电机和传动
→ 现实输入 u_real
```

两者可能因为下面这些因素不同：

- 电流或力矩饱和；
- 电池电压下降；
- 温度保护；
- 通信延迟或丢包；
- 摩擦、齿隙和结构柔性；
- 驱动器内部还有一层位置或电流控制。

所以 Controller 输出“正确命令”，仍不等于真实机器人必然产生期望运动。

## 3. 跟踪一个真实控制周期

现在把时间放慢，观察机器人走向厨房时的某一个 `1 ms` 控制周期。

### 第一步：传感器带回现实证据

上一条命令已经作用于机器人。IMU、编码器和足底传感器产生带时间戳的测量：

```text
y[k]
```

这里 `k` 是当前离散控制周期编号。

### 第二步：估计器更新当前判断

估计器使用：

```text
旧估计 x_hat[k-1]
+ 上一周期发出的命令 u[k-1]
+ 当前测量 y[k]
+ 内部模型
```

得到：

```text
x_hat[k]
```

它还可能更新接触可信度，例如“右脚大概率已经接地，但出现侧向滑动迹象”。

### 第三步：读取仍然有效的运动参考

步态规划器不一定每 `1 ms` 都更新。控制器读取最近一次有效参考，并检查：

- 参考属于哪个时间；
- 是否已经过期；
- 当前应处于左支撑、右支撑还是双支撑；
- 摆动脚此刻应该在哪里；
- 质心和躯干此刻应该怎样运动。

### 第四步：控制器计算候选命令

控制器比较参考和 `x_hat[k]`，结合动力学、接触和硬件限制，计算：

```text
u_candidate[k]
```

下标 `candidate` 强调它仍是准备下发的候选命令。

### 第五步：安全层检查

安全层检查候选命令是否包含：

- NaN（Not a Number，非法数值）或无穷大；
- 超过位置、速度、力矩上限的数；
- 相邻周期变化过大的跳变；
- 与当前状态机不相容的模式；
- 已过期的上层命令。

通过检查后，才形成最终下发命令：

```text
u[k]
```

### 第六步：真实世界给出结果

驱动器尝试执行 `u[k]`，形成现实输入 `u_real[k]`。机器人、重力、接触和扰动共同决定新的真实状态：

```text
x_real[k+1]
```

下一周期，传感器再把这个结果的一部分带回来。

这六步不断循环。所谓系统架构，最终必须落实到这条真实时间线上，而不只是画几个方框。

## 4. 右脚打滑时，整套系统怎样协作

现在让主线出现一次故障。

规划器认为：

```text
12.37 s：右脚已经落地并开始承重
```

但真实地面上有一小块光滑区域。右脚接触以后向外滑动。

### 4.1 现实先发生，软件随后才知道

真实顺序是：

```text
右脚接触光滑地面
→ 地面实际摩擦不足
→ 右脚向外滑
→ 身体产生额外侧倾和角速度
→ 传感器出现异常证据
```

规划器写出的接触计划不会阻止脚滑。接触计划是期望，真实摩擦属于 `f_real`。

### 4.2 估计器不能只相信“计划说已经踩稳”

估计器可能同时看到：

- 足底法向力上升，说明脚确实碰到了地面；
- 运动学推算的足端速度却不接近零；
- IMU 检测到身体侧向角速度增加；
- 关节与足底受力关系不符合稳定支撑。

于是接触状态不应该只有一个绝对 `bool`。更完整的判断可能是：

```text
右脚接触概率：0.96
右脚疑似滑动：true
右脚法向力估计：180 N
```

这表达的是：“脚确实碰地了，但这条接触不能被当成牢固固定点。”

### 4.3 高频控制器先处理眼前危险

新的 `x_hat` 表明身体正在侧倾。高频控制器可能立即：

- 调整左右脚受力分配；
- 改变躯干和手臂动作；
- 降低横向速度目标；
- 若仍来得及，修改下一只脚的动作参考。

这一步处理的是“当前几毫秒还能做什么”。

### 4.4 规划器重新安排未来几步

较低频的规划器收到新的状态和接触判断后，可能：

- 缩小下一步步幅；
- 把落脚点移向身体倾倒方向；
- 延长双支撑阶段；
- 取消继续加速的计划。

它处理的是“接下来几十到几百毫秒怎样恢复”。

### 4.5 超出恢复能力时，安全层改变目标

如果滑动发展太快，继续追求“按原速度去厨房”已经不合理。系统应把优先级改成：

```text
先避免危险动作
→ 尽量降低冲击
→ 必要时进入阻尼或受控倒地
```

安全停止不是导航或行走任务的成功，却可能是整个机器人系统在不可恢复条件下的正确控制选择。

这段故事说明各层不是互相替代，而是处理不同时间范围的问题：

```text
估计器：现实究竟发生了什么
高频控制器：眼前还能怎样救
规划器：未来几步怎样改
状态机与安全层：当前任务是否还应该继续
```

## 5. 数据接口：模块之间究竟传什么

上一节中的故事如果没有明确接口，就无法实现或回放。下面是一组示意数据结构：

```go
type ContactEstimate struct {
	IsContact     bool    // 当前最可能的离散接触判断
	Probability   float64 // 接触可信度，范围 0～1
	SlipSuspected bool    // 是否怀疑接触点正在打滑
	NormalForce   float64 // 估计法向力，单位 N
}

type EstimatedState struct {
	Timestamp           int64      // 该状态估计对应的采样时刻
	BasePosition        Vec3       // 基座在世界系中的位置，单位 m
	BaseOrientation     Quaternion // 基座相对世界的姿态；分量顺序由接口规定
	BaseLinearVelocity  Vec3       // 本例约定用世界系表达，单位 m/s
	BaseAngularVelocity Vec3       // 本例约定用身体系表达，单位 rad/s
	JointPosition       Vector     // 关节位置，单位 rad，顺序由模型规定
	JointVelocity       Vector     // 关节速度，单位 rad/s，顺序同上
	Contacts            []ContactEstimate
}

type MotionReference struct {
	Timestamp        int64
	BaseTrajectory   Trajectory
	FootTrajectories []Trajectory
	ContactSchedule  ContactSchedule
}

type JointCommand struct {
	Timestamp int64
	Mode      DriveMode // torque、position 或 hybrid 等
	Torque    Vector    // 力矩命令或前馈项，单位 N·m
	Position  *Vector   // 可选位置命令，单位 rad
	Velocity  *Vector   // 可选速度命令，单位 rad/s
}
```

它们不是可以直接复制的行业标准。真正接口还必须规定：

- 四元数顺序是 `[w,x,y,z]` 还是 `[x,y,z,w]`；
- 每个位置、速度、力在哪个坐标系表达；
- 关节顺序、零位和正方向；
- 时间戳使用哪个时钟；
- 数据多久以后算过期；
- `Torque` 是前馈项还是最终命令；
- 不同驱动模式下各字段怎样组合；
- 接触可信度和状态估计不确定性怎样表达。

变量命名还应明确区分：

```text
measurement：传感器测量
estimate：根据证据得到的估计
reference / desired：希望跟踪的参考
candidate：尚未下发的候选答案
command：准备或已经下发的命令
ground truth：真值，通常只在仿真或外部测量中获得
```

若日志里所有东西都叫 `state` 或 `action`，右脚打滑以后就很难判断：到底是测量错、估计错、参考错，还是电机没跟上命令。

## 6. 为什么不同模块运行频率不同

机器人没有必要每 `0.1 ms` 重新规划去厨房的全局路径，但电机电流必须非常快地调整。

典型数量级示意：

| 模块 | 频率示例 | 每次主要更新什么 |
|---|---:|---|
| 全局导航 | `1～10 Hz` | 地图路径 |
| 步态与轨迹规划 | `20～100 Hz` | 落脚点和身体参考 |
| MPC | `30～200 Hz` | 未来状态或接触力参考 |
| WBC | `500～1000 Hz` | 当前全身协调和关节命令 |
| 电机电流环 | `5～20 kHz` | 电机相电流 |

这些只是数量级，不是统一标准。

假设规划器 `50 Hz` 更新一次，也就是每 `20 ms` 给出一份新参考；WBC 以 `1 kHz` 运行，在这 `20 ms` 中会执行约 20 次。它不能停下来等待规划器，而要读取最近一份仍有效的参考，在每个小周期中根据最新 `x_hat` 持续纠偏。

因此跨频率接口必须处理：

- **时间戳**：这份数据对应哪个时刻；
- **插值**：两个参考点之间应该怎样平滑取值；
- **保持**：新参考没来时是否短暂沿用旧值；
- **数据过期**：旧到什么程度必须拒绝；
- **时钟同步**：不同设备的时间是否对齐；
- **线程安全**：高频控制器读取时数据不能被写坏；
- **超时降级**：上层停止更新时，低层不能无限执行旧命令。

频率高不等于延迟小。一个模块每毫秒运行一次，却始终处理 50 ms 前的测量，仍然是在高速使用过时信息。

学习控制也会遇到同一问题。例如策略每 `20 ms` 推理一次，也就是 `50 Hz`；底层关节命令通道却需要每 `2 ms` 更新一次，也就是 `500 Hz`。一种明确做法是零阶保持：

```text
50 Hz 策略产生一组新关节目标
→ 500 Hz 发送线程在接下来 10 个周期重复最新目标
→ 下一次策略输出到来后再替换
```

零阶保持不是“底层又算了十次策略”，只是把最近一次有效命令持续送到需要更高更新率的接口。实现时仍要定义：新命令怎样原子替换、策略超时以后保持多久、发送线程死亡由谁发现，以及是否允许插值。策略频率、发送频率和保持方式共同构成部署时序契约。

## 7. 状态机：系统当前允许做什么

同一套机器人在开机、校准、站立和行走时，允许执行的动作不同。

常见运行状态：

```text
BOOT
→ CALIBRATE
→ STAND_UP
→ STAND
→ WALK
→ STOP
→ DAMPING / EMERGENCY
```

- `BOOT`：软件和硬件启动；
- `CALIBRATE`：确认关节零位、传感器偏置等；
- `STAND_UP`：从初始姿态起身；
- `STAND`：稳定站立并等待任务；
- `WALK`：执行行走；
- `DAMPING`：以阻尼为主，减少继续主动发力造成的危险；
- `EMERGENCY`：进入预先设计的紧急处理。

状态不能只凭一句命令随意跳转。每次切换都应检查守卫条件：

- 关节是否完成校准；
- 状态估计器是否已经稳定；
- 姿态是否在安全范围；
- 双脚接触是否可信；
- 控制器和通信是否持续健康；
- 上一个动作是否已经结束。

不要把“机器人运行状态机”和“步态接触相位”混成一件事。行走状态 `WALK` 内部还会有：

```text
双支撑
→ 左脚支撑、右脚摆动
→ 双支撑
→ 右脚支撑、左脚摆动
```

前者决定系统当前是否允许行走；后者描述行走过程中哪只脚应该接触。

右脚严重打滑时，系统可能先改变接触相位和步态参考；若恢复失败，再从 `WALK` 切换到 `DAMPING`。这是两个时间尺度不同的状态变化。

### 7.1 控制权：状态机说“我在控制”还不够

软件内部把枚举值改成 `WALK`，不能证明真实硬件已经把控制权交给这段程序。机器人上可能同时存在厂商运动服务、用户控制器、调试进程和原始关节命令发布者。若两者同时写同一个命令通道，结果不是“谁更聪明谁赢”，而是时序不可预测。

控制权交接至少应是一段可观测的握手：

```text
先准备好安全的零运动/保持命令，但不争抢命令通道
→ 请求原控制服务释放或切换模式
→ 等待硬件返回确认 ACK
→ 检查命令通道中没有第二个活跃发布者
→ 当前控制器先发送安全命令，再进入 ACTIVE
```

- ACK 是 acknowledgement，确认回执；它表示对方确实完成了请求，不只是本程序“已经发过请求”；
- publisher 是向命令通道写数据的发布者；同一执行器在同一时刻通常只能有一个明确的控制所有者；
- ownership 是控制权归属，回答“此刻谁有资格发命令”。

退出也不能只写 `process.exit()`：

```text
先进入阻尼或安全保持
→ 停止自己的命令发布
→ 请求恢复原生安全模式
→ 等待恢复 ACK
```

主控制进程崩溃时，它已经没有机会执行这段退出代码。因此还需要独立看门狗或系统服务在进程超时、异常退出后执行恢复动作。状态机描述“系统想处于什么模式”，控制权握手和外部监督才证明“真实命令通道现在由谁掌握”。

## 8. 安全层和日志：失败时怎样不靠猜

### 8.1 安全层不是万能控制器

命令下发前常经过：

```text
非法数值检查
→ 位置、速度和力矩限幅
→ 命令变化率限制
→ 姿态与碰撞检查
→ 通信和时间戳检查
→ 下发
```

- `NaN`：Not a Number，非法数值；
- `Inf`：Infinity，无穷大；
- 变化率限制：限制相邻周期的命令跳变，而不只限制命令绝对值。

安全层能挡住很多软件故障，却不能证明机器人在所有未知地面上都不会摔倒。动态平衡涉及未来演化，不能只靠最后一道数值限幅解决。

常见降级策略：

- 新命令超时：不再继续执行陈旧行走参考；
- 状态估计失效：切换到适当的阻尼或停止策略；
- 求解器短时失败：有限时间使用上一安全结果；
- 连续失败：停止任务并进入降级状态；
- 姿态超出恢复区域：减少主动刚性，保护关键结构；
- 通信丢失：驱动器本地看门狗触发。

看门狗（watchdog）会检查规定时间内是否持续收到有效更新。它不是在“理解机器人”，只是防止上层已经失联时底层还永远保持最后一条危险命令。

### 8.2 安全层会改变闭环，不是透明包装

第 3 节把安全检查写成：

```text
u_candidate[k]
→ 安全裁剪或限速
→ u[k]
→ 真实机器人
→ 下一周期测量
```

只要 `u[k]` 与 `u_candidate[k]` 不同，机器人下一步到达的状态就不同，控制器下一次看到的观测也会不同。安全层因此已经进入被控制对象的闭环动态，而不是一个“只在出错时才存在”的透明外壳。

限制太松会放过危险跳变；限制太紧也可能拿走维持平衡所需的控制权。例如位置目标相对实测关节最多只能偏 `0.25 rad`，位置增益 `K_p=28.5 N·m/rad` 时，仅比例项最多只能请求约：

```text
28.5 × 0.25 ≈ 7.1 N·m
```

若正常承重本来需要二十多牛米，机器人就可能“电机已使能、动作也在变化，却撑不起来”。这时不能简单认定策略失效。

安全层上线前应做受控 A/B，也就是保持模型、初始状态和命令相同，只切换待比较的保护配置。分别比较原始候选命令和不同保护配置；日志至少保留原始目标、保护后目标、每项裁剪原因、修正幅度和触发比例。安全的目标不是“把所有命令压得越小越好”，而是在不移除正常控制能力的前提下阻止明确越界。

### 8.3 用日志重建右脚打滑事件

至少记录：

- 原始传感器测量和时间戳；
- 状态估计、协方差和接触可信度；
- 导航路径和运动参考；
- 控制器任务误差；
- 求解器状态、耗时和约束余量；
- 下发前后的命令及裁剪结果；
- 电机位置、速度、力矩、电压和温度反馈；
- 状态机与接触相位切换事件。

有了统一时间轴，才能重建：

```text
12.368 s：规划参考要求右脚落地
12.371 s：足底法向力上升
12.373 s：估计足端横向速度异常
12.374 s：SlipSuspected 变为 true
12.375 s：控制器开始重新分配接触力
12.390 s：规划器缩短下一步
```

若日志没有统一时间戳，只看“脚滑了”和“命令变了”两条曲线，就无法判断是控制器先发错命令导致滑动，还是脚先滑、控制器随后才作出补救。

日志不是为了事后堆数据，而是保存因果证据。

## 9. 端到端会不会让这些模块消失

“端到端”必须先问清两端是什么：

- 本体观测 → 关节目标：可能合并步态规划和部分控制；
- 相机图像 → 关节目标：还合并部分感知；
- 语言命令 → 全身动作：覆盖更长的任务链。

网络可以改变算法边界，却不会删除现实中的这些问题：

- 传感器仍要采样和同步；
- 电机仍有电流、温度和力矩限制；
- 通信仍会延迟和丢包；
- 开机仍要校准；
- 任务仍可能超时；
- 故障仍要安全降级；
- 训练外情况仍需要检测和记录。

因此“端到端”通常表示某些决策模块由一个模型共同实现，不表示真实系统只剩一个神经网络进程。

工程中还可能出现不同组合：

### 全身遥操作 → 数据 → VLA

VLA 是 Vision-Language-Action，视觉—语言—动作模型。先用可靠遥操作系统采集全身数据，再训练条件化策略。主要困难是真机数据昂贵、遥操作本身也需要稳定低层控制。

### 上下肢分离

下肢策略负责行走，上肢按机械臂方式操作。轻载时结构清楚；搬重物或大幅弯腰时，上肢会显著改变质心和角动量，分离假设可能失效。

### Navigation + Planning + 通用 Controller

导航负责路径，上层方法生成动作或落脚参考，通用控制器负责动力学可行和高频抗扰。它保留清楚接口，也允许各层分别使用传统方法或学习方法。

不存在脱离任务约束的唯一最佳架构。判断架构时应问：每层看见什么、输出什么、更新多快、失败由谁发现、由谁恢复。

## 10. 最后用三个闭环压缩整套系统

### 物理环

```text
驱动器与电机
→ 真实刚体和接触运动
→ 传感器测量
```

### 估计环

```text
传感器测量
+ 旧估计、旧命令和内部模型
→ 当前状态估计 x_hat
```

### 决策环

```text
人的目标和运动参考
+ 当前状态估计 x_hat
+ 模型与限制
→ 当前命令 u
```

三个环运行在一起：

```text
目标 → 导航与规划 → 参考 ─────────────┐
                                     ↓
测量 y → 状态估计 → x_hat → 控制器 → 命令 u
  ↑                                  ↓
  └──── 真实机器人与环境 ← u_real ← 驱动器
```

右脚打滑时，物理环首先改变；估计环把变化变成当前判断；决策环改变动作；若恢复能力不足，状态机和安全层改变整个任务状态。

这就是一套人形控制系统真正的整体叙事。

## 本章小结

1. “去厨房”必须依次翻译成路径、运动参考和当前关节命令；任何一层输出都不是现实结果的保证。
2. 传感器提供测量 `y`，估计器形成 `x_hat`，控制器生成命令 `u`，驱动器和硬件最终实现 `u_real`。
3. 高频控制器处理眼前扰动，规划器调整未来几步，状态机和安全层决定任务是否还能继续。
4. 多频率模块必须通过时间戳、数据有效期、插值和超时策略协作。
5. 日志必须能在同一时间轴上重建“现实先发生什么、软件随后知道什么、控制器又做了什么”。

## 练习

1. “去厨房”“下一步右脚落点”“当前右膝力矩”分别主要由哪一层决定？
2. 规划器说右脚已经进入支撑相，为什么估计器仍要检查真实接触？
3. 为什么 `50 Hz` 规划器可以和 `1 kHz` 控制器一起工作？
4. 右脚打滑后，估计器、控制器、规划器和安全层分别负责什么？
5. 为什么只有命令和最终姿态日志，仍不足以判断摔倒原因？
6. 为什么内部状态已经切到 `WALK`，仍不能证明当前程序拥有真实控制权？
7. 为什么把动作变化率限制调得更小，不一定更安全？

参考答案：

1. 导航、运动规划、当前控制器。
2. 接触计划只是参考；现实可能提前、延后、落空或打滑。
3. 控制器在两次规划更新之间读取最近的有效参考，并依据最新状态估计高频纠偏。
4. 估计器判断真实状态；控制器处理眼前恢复；规划器修改未来几步；安全层决定是否限幅、降级或停止。
5. 缺少测量、估计、参考、接触和时间戳，就无法区分错误从哪一层开始以及各事件的先后顺序。
6. 控制权还需要硬件模式确认、命令发布者排他检查和 ACK，内部枚举只是本程序自己的判断。
7. 过严限制会改写闭环并移除平衡所需的控制能力，必须在保留正常能力与阻止越界之间用 A/B 证据选择。
